# v0.1 release status

This document is the release-readiness summary for the roadmap in
[v0.1 implementation roadmap](v0.1-implementation-roadmap.md).

The implementation is intentionally still identified as `0.1.0-dev`.
The software implementation through the qualification/publication pipeline is
complete on `main`. The remaining roadmap work is hardware-gated: compile and
exercise the Pi/libcamera backend, run the official six-camera campaign, and
promote its evidence. The project must not publish a final v0.1 hardware
capability dataset before those runs exist.

## Host validation completed

The host-safe portion has been validated without GitHub Actions:

- library-only CMake configure/build succeeds without libcamera installed;
- the host-safe core/raw build was re-run with GCC 14 and CTest reported 2/2 passing tests;
- HSCAP/raw reconstruction tests include RAW10/RAW12 packing, padded stride, all Bayer orders, odd-origin phase, exact bilinear demosaic, monochrome rendering and truncation rejection;
- interrupted HSCAP recovery is covered;
- exact 64-bit timestamp metadata round-trips;
- qualification promotion policy has host-side unit coverage for dirty-source rejection, plan provenance, visual-evidence requirements, recovery failures and pass-case timing evidence;
- `cmake --install` installs the library and headers;
- a separate downstream CMake project can use
  `find_package(hscam 0.1 REQUIRED CONFIG)` and link
  `hscam::hscam` and `hscam::raw`.

The local mounted workspace did not contain the newest remote promotion code,
so the latest promotion hardening was source-reviewed and accompanied by
updated unit-test fixtures in the repository, but was not executed in that
local snapshot.

These checks do **not** validate the Raspberry Pi/libcamera capture backend.

## Required Raspberry Pi validation

Before changing the version string to final `0.1.0`, at minimum:

1. build on the canonical Raspberry Pi OS environment with
   `HSCAM_REQUIRE_LIBCAMERA=ON`;
2. run the host/unit test suite on that Pi;
3. run `hscam-inspect` and normal advertised-mode capture;
4. verify the IMX296 sensor-crop path without `media-ctl`;
5. produce and visually inspect a real HSCAP/PNG/DNG/video sequence;
6. run the committed official qualification manifest for every official
   sensor family;
7. promote only valid clean-revision runs with `hscam-qualify promote`;
8. run `hscam-qualify audit-results --results-root qualification/results`
   and resolve every missing/invalid official sensor entry.

A camera that does not support mutable sensor crop is still a valid completed
result: its advertised modes and the absence of mutable crop are part of the
dataset.

The completeness gate accepts an explicit `blocked.json` only when a sensor
campaign genuinely could not be completed and the record contains a
non-empty, reviewable reason. Missing sensors are not treated as blocked.

## Result promotion

Working campaign output belongs under `qualification/work/`.

A valid run is promoted with:

```bash
build/hscam-qualify promote \
  qualification/work/imx296 \
  --results-root qualification/results
```

Promotion enforces the publication gate:

- campaign status must be valid;
- result schemas must be recognized;
- the deterministic plan ID must recompute from the exact manifest text,
  camera ID, hscam version and clean source revision;
- the aggregate case set must match the frozen plan;
- every passing case must retain its per-frame timing trace;
- start/end environment, advertised-mode crop snapshots and result artifacts
  must exist;
- a recovery failure blocks publication;
- enabled visual evidence requires actual PNG files and at least one video;
- raw crop-probe, per-case and FPS-search evidence is retained;
- large raw `.hscap` sample bundles are omitted from Git by default while
  derived evidence and result provenance are retained.

## Release blockers

### Physical hardware data

The official six-camera campaign has not been executed by this repository yet.
No high-FPS number should be presented as a project measurement until its
promoted result exists under `qualification/results/`. The official campaign
also requires a local `ffmpeg` executable because video evidence is part of
the publication gate; libtiff/DNG remains optional.

### License selection

The repository currently has no explicit `LICENSE` file. Choosing a software
license is a project-owner decision and is intentionally not guessed by the
implementation work.

A license should be selected before the project is presented as a normal
reusable open-source release or before accepting outside contributions under
an assumed license.

### Final version/tag

Keep:

```text
HSCAM_VERSION_STRING = 0.1.0-dev
```

until the hardware campaign and license decision above are complete. Then run
the final release gate from the roadmap, change the version string to
`0.1.0`, and create the release/tag deliberately.

## What is not a blocker for the hardware campaign

The following are intentionally post-v0.1 concerns:

- Python bindings;
- OpenCV integration;
- Movidius/OpenVINO;
- live preview UI;
- raw-stream compression;
- advanced ISP-quality demosaic/colour processing;
- a stable plugin ABI;
- automated cloud hardware testing.

The v0.1 architecture is designed so those can be added without changing the
scientific capture/qualification boundary.

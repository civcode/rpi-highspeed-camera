# v0.1 implementation roadmap

## Purpose

This document defines the implementation order for the first usable version of `rpi-highspeed-camera`.

The roadmap turns the existing design documents into an executable sequence of milestones with explicit deliverables and acceptance criteria.

The v0.1 goal is not merely to expose libcamera through another wrapper. The first version is complete when the project can:

1. discover and describe an official Raspberry Pi camera;
2. configure and capture an advertised sensor mode;
3. apply and verify a sensor-level crop when the driver exposes that capability;
4. capture frames with enough metadata to measure the real delivered frame rate;
5. store a self-describing raw sequence;
6. reopen that sequence and render a correct still image;
7. export a slow-motion verification video;
8. execute a reproducible qualification manifest for the official Raspberry Pi cameras;
9. publish the resulting measurements and representative visual artifacts.

The timing-critical capture core and the one-time qualification machinery remain separate.

---

# 1. v0.1 scope

## Included

The first version includes:

- C++20 core library;
- CMake build;
- generic libcamera camera discovery;
- advertised sensor-mode discovery;
- media-controller/V4L2 sensor-subdevice discovery;
- runtime crop capability detection;
- raw capture;
- optional processed-stream capture where required for diagnostics;
- exact-vs-adjusted configuration reporting;
- bounded request/buffer lifecycle;
- sensor timestamps and frame-loss statistics;
- self-describing HSCAP capture bundles;
- raw Bayer/mono unpacking;
- deterministic still-image rendering;
- PNG export;
- representative DNG export;
- slow-motion video export;
- a manifest-driven official-camera qualification runner;
- versioned machine-readable qualification results;
- generated Markdown summary tables.

## Explicitly deferred

The following are not v0.1 requirements:

- Python bindings;
- OpenCV dependency;
- graphical live preview;
- hardware-accelerated computer vision;
- Movidius/OpenVINO integration;
- compression of the raw capture stream;
- sophisticated photographic ISP reproduction;
- plugin ABI;
- automatic kernel patching;
- undocumented sensor-register programming;
- dynamic cloud result submission;
- GitHub Actions hardware execution;
- supporting every possible third-party camera before the official-camera campaign.

Third-party sensors should work when the generic APIs are sufficient, but the v0.1 release gate is based on the official Raspberry Pi camera families.

# 2. Definition of done

v0.1 is complete when the following end-to-end command flow works on a Raspberry Pi:

```text
hscam-inspect
      |
      v
camera + mode + capabilities identified
      |
      v
hscam-capture
      |
      v
capture.hscap
      |
      +--> hscam-export image --> PNG
      |
      +--> hscam-export dng   --> DNG
      |
      +--> hscam-export video --> MP4/MKV
      |
      v
qualification runner
      |
      v
versioned JSON results + Markdown summary
```

For IMX296, the release must additionally demonstrate one known high-FPS sensor-crop configuration without invoking `media-ctl` as a subprocess.

For cameras that do not expose arbitrary sensor crop, the release must correctly report that limitation and benchmark their advertised sensor modes instead.

# 3. Development principles

These rules apply throughout the roadmap.

## 3.1 Keep the capture core small

`libhscam` owns:

- discovery;
- negotiation;
- capture;
- buffer lifetime;
- timing metadata.

It does not own:

- image rendering;
- video encoding;
- qualification policy.

## 3.2 Make adjustments observable

Every configuration has:

```text
requested state
negotiated state
```

If the kernel or libcamera changes a crop, format, stride, buffer count, or timing value, that adjustment is visible.

## 3.3 Never use visual output as timing evidence

PNG/video confirms that payload bytes reconstruct into sensible imagery.

Sensor timestamps, request metadata, sequence numbers, and queue statistics determine whether a high-FPS capture is valid.

## 3.4 Prefer simple implementations until measurement proves they are insufficient

Examples:

- bounded mutex/condition-variable queue before lock-free structures;
- bilinear demosaic before advanced interpolation;
- directory-based HSCAP before a custom archive/container;
- direct JSON/JSONL result files before a database.

## 3.5 Hardware tests are explicit

No GitHub Actions workflow is required for hardware execution.

Hardware-dependent tests are run directly on the Raspberry Pi.

Host/unit tests should run locally wherever possible.

# 5. Phase 0 — project foundation

## Goal

Create a buildable C++ project with stable conventions before camera code spreads through the repository.

## Deliverables

- top-level `CMakeLists.txt`;
- C++20 requirement;
- compiler warnings enabled;
- `libhscam` target;
- unit-test target;
- simple version header;
- error/result conventions;
- core value types:
  - `Size`;
  - `Rect`;
  - `PixelFormat`;
  - duration aliases;
- formatting/lint conventions documented;
- basic README build instructions.

Core runtime dependency:

- libcamera;
- Linux media/V4L2 headers.

Do not add FFmpeg, OpenCV, or PNG dependencies to `libhscam`.

## Unit tests

At minimum:

- rectangle equality/intersection/validation;
- value-type serialization where relevant;
- deterministic mode-ID helper;
- error formatting.

## Acceptance gate

A clean checkout can be configured and built locally with one documented CMake command.

All host-only unit tests pass.

No camera is required yet.

## Recommended checkpoint commit

```text
build: add C++ project skeleton and core value types
```

# 7. Phase 2 — normal capture path

## Goal

Capture an advertised libcamera mode with deterministic frame ownership and measurable timing.

## Deliverables

Implement:

- `Camera` state machine;
- `CaptureRequest`;
- `CaptureConfiguration`;
- exact-vs-adjusted negotiation policy;
- libcamera stream configuration;
- `FrameBufferAllocator`;
- fixed request pool;
- buffer mmap;
- request-completion handling;
- bounded completed-frame queue;
- `CaptureSession`;
- move-only `FrameLease`;
- `FrameMetadata`;
- lightweight `CaptureStats`.

Add:

```text
hscam-capture
```

Initial smoke-test mode:

```bash
hscam-capture \
  --camera <id> \
  --mode <mode-id> \
  --frames 10000 \
  --discard-payload
```

## Required behavior

The completion callback only:

- reads metadata;
- records lightweight status;
- queues the completed request token.

No disk I/O, demosaic, encoding, or arbitrary user processing runs in the completion callback.

## Unit tests

- state-machine transitions;
- adjustment comparison;
- exact-policy rejection;
- bounded queue behavior;
- frame-lease move/destruction semantics;
- sequence-gap detection;
- timestamp/FPS calculations.

## Hardware tests

- start/stop repeatedly;
- capture fixed frame count;
- intentionally hold leases until buffers starve;
- verify starvation is observable;
- verify queue overrun is observable;
- verify measured FPS derives from timestamps rather than requested controls.

## Acceptance gate

An advertised raw mode captures for at least 30 seconds with:

- no library crashes;
- no hidden queue overwrite;
- every frame carrying usable metadata;
- clean stop/release;
- reported measured FPS.

## Recommended checkpoint commits

```text
feat: add libcamera capture configuration
feat: add persistent request and frame lease lifecycle
feat: add capture timing statistics
```

# 8. Phase 3 — media graph and generic sensor control

## Goal

Replace the external `media-ctl` part of existing high-FPS hacks with direct C++ code.

## Deliverables

Implement:

- media-device enumeration;
- media entity/pad discovery;
- association between selected libcamera camera and its sensor subdevice;
- `SensorSubdevice`;
- V4L2 subdevice format queries;
- selection target queries:
  - native size;
  - crop bounds;
  - crop default;
  - current crop;
- TRY-state crop negotiation;
- ACTIVE crop configuration;
- requested-vs-negotiated crop result;
- snapshot/restore of relevant sensor state.

Extend `CameraCapabilities` with observed support for:

- crop query;
- TRY crop;
- ACTIVE crop;
- exact crop.

## Critical design constraint

No hard-coded:

- `/dev/mediaN`;
- `/dev/v4l-subdevN`;
- I2C bus/address;
- IMX296-only device path.

Sensor-name quirks are allowed only after a concrete generic failure has been demonstrated and documented.

## Acceptance gate

On a camera with no arbitrary crop support:

- the library reports the limitation cleanly;
- normal advertised-mode capture still works.

On IMX296:

- the library can set and re-read one known sensor crop without spawning `media-ctl`.

## Recommended checkpoint commits

```text
feat: discover camera media graph and sensor subdevice
feat: add generic V4L2 sensor crop negotiation
```

# 9. Phase 4 — integrate sensor crop with libcamera capture

## Goal

Make sensor-level configuration survive the complete libcamera configuration/start sequence.

## Deliverables

Establish and encode the correct operation order for:

1. camera acquisition;
2. libcamera configuration generation;
3. libcamera validation;
4. sensor format/crop negotiation;
5. libcamera configure;
6. crop verification;
7. buffer allocation;
8. capture start.

If the required order differs by pipeline/kernel behavior, isolate that logic internally.

Add explicit errors for:

- crop lost after libcamera configuration;
- exact crop changed;
- incompatible stream/crop request;
- camera recovery failure.

## Primary regression

Use the published IMX296 case:

```text
1456 x 96
~536 fps target
```

as the first strong regression.

The library must not special-case that geometry.

## Acceptance gate

For the IMX296 reference run:

- requested crop is set through `libhscam`;
- negotiated crop is read back and recorded;
- capture starts;
- sensor timestamps are collected;
- queue overruns are zero during a discard-payload run;
- measured frame rate is reported;
- no `media-ctl` or `rpicam-vid` subprocess is used.

The exact measured FPS is hardware/software dependent and is not hard-coded as a pass condition during library development.

## Recommended checkpoint commit

```text
feat: integrate sensor crop with libcamera capture
```

# 10. Phase 5 — HSCAP self-describing capture

## Goal

Make raw captures reproducible and reopenable without external knowledge of the camera configuration.

## Deliverables

Implement HSCAP v1 directory format:

```text
capture.hscap/
    manifest.json
    frames.bin
    frames.idx
    metadata.jsonl
```

Implement:

- `BundleWriter`;
- `BundleReader`;
- versioned manifest;
- exact stream/camera/sensor configuration recording;
- explicit frame offsets and lengths;
- per-frame metadata;
- graceful finalization;
- detection of incomplete/truncated captures.

Add capture mode:

```bash
hscam-capture ... --output capture.hscap
```

## Design constraints

The stored frame payload is exactly the selected captured stream payload.

Do not:

- debayer;
- repack;
- normalize;
- strip padding silently.

The manifest must describe enough layout information for the reader to reconstruct rows correctly.

## Unit tests

- manifest round-trip;
- frame index round-trip;
- explicit byte-order tests;
- random access to frame N;
- truncated payload detection;
- interrupted/incomplete bundle detection;
- mismatched manifest/index rejection.

## Acceptance gate

A capture can be closed, the process exited, and the bundle reopened by a new process that can report:

- camera;
- sensor mode/crop;
- pixel format;
- size;
- stride/plane lengths;
- frame count;
- per-frame timestamps.

No command-line width/height/format hints are required.

## Recommended checkpoint commits

```text
feat: add HSCAP v1 bundle format
feat: write raw capture bundles
```

# 11. Phase 6 — raw reconstruction and PNG verification

## Goal

Prove visually that stored raw payloads reconstruct correctly.

## Deliverables

Add separate raw/rendering code, not a dependency of `libhscam`.

Implement:

- raw layout description;
- 8-bit raw unpack path;
- packed/unpacked 10-bit support;
- packed/unpacked 12-bit support;
- 16-bit path where applicable;
- monochrome path;
- Bayer orders:
  - RGGB;
  - GRBG;
  - GBRG;
  - BGGR;
- row-stride handling;
- crop/Bayer-phase handling;
- black/white normalization;
- deterministic bilinear demosaic;
- neutral preview render;
- PNG output.

Add:

```bash
hscam-export image capture.hscap \
  --frame 100 \
  --output frame.png
```

## Required synthetic tests

At minimum:

- known RAW10 packing vector;
- known RAW12 packing vector;
- padded rows;
- every Bayer order;
- odd/even crop origin;
- truncated row;
- known 4x4 or 8x8 Bayer image with exact expected demosaic result;
- monochrome image.

## Hardware visual test

Use a repeatable scene containing:

- horizontal/vertical lines;
- diagonal edges;
- text;
- RGB/gray patches.

Check for:

- wrong stride;
- row corruption;
- wrong Bayer phase;
- orientation errors;
- gross colour failure.

## Acceptance gate

A representative raw frame from each available sensor can be converted to a geometrically correct PNG.

The renderer does not need to match Raspberry Pi ISP photographic quality.

## Recommended checkpoint commits


# 12. Phase 7 — DNG and video export

## Goal

Create interoperable raw stills and human-reviewable slow-motion sequences.

## DNG deliverables

Implement DNG export using the stored raw payload and available metadata.

Record where available:

- image dimensions;
- Bayer pattern;
- bit depth;
- black/white levels;
- exposure;
- gain;
- white balance;
- colour matrix;
- relevant crop information.

Validate representative files in at least two independent DNG-capable applications.

## Video deliverables

Add optional FFmpeg/libav dependencies to `hscam-export`, not to `libhscam`.

Implement:

```bash
hscam-export video capture.hscap \
  --output preview.mp4 \
  --playback-fps 30
```

Required timing modes:

- fixed playback rate for slow motion;
- sensor-timestamp-derived real-time presentation.

For fixed playback rate, every stored frame appears once, in sequence.

If a captured sequence contains a timing gap, the exporter does not invent a missing source frame.

## Acceptance gate

A high-FPS HSCAP sequence can produce:

- one valid DNG;
- one valid PNG;
- one playable 30/60-fps slow-motion video.

The capture core remains buildable without FFmpeg.

## Recommended checkpoint commits

```text

feat: add slow-motion video export
```

# 13. Phase 8 — qualification engine

## Goal

Build the one-time, rigorous official-camera test machinery on top of the now-stable core.

This is not designed as a casual end-user command.

The central abstraction is a **qualification manifest**, not a collection of ad-hoc CLI flags.

## Deliverables

Implement a campaign runner that accepts a version-controlled manifest such as:

```yaml
schema: 1
campaign: official-rpi-cameras-v1

environment:
  require_no_throttling: true

tests:
  advertised_modes:
    enabled: true

  sensor_crop:
    discover_geometry: true
    characterize_position_dependence: true

  fps_search:
    enabled: true

  validation:
    short_duration_s: 10
    final_duration_s: 60
    require_zero_drops: true
```

The exact schema should be finalized before campaign execution.

Implement:

- fixed test-plan parsing;
- environment snapshot;
- camera fingerprint;
- resumable execution;
- isolated worker process per risky active test;
- hard timeout;
- restoration verification;
- baseline health check after failures;
- advertised-mode characterization;
- crop capability discovery;
- crop geometry discovery;
- FPS search;
- strict final validation;
- raw result persistence;
- deterministic report generation.

## Important change from the early CLI concept

The campaign runner should not encourage arbitrary interactive commands such as:

```text
hscam-test crop ...
```

as the primary interface.

For the official-camera run, every test should come from the committed manifest so the complete campaign can be reproduced and audited.

Low-level single-case commands may exist for development/debugging, but they are not the scientific protocol.

## Acceptance gate

A campaign interrupted midway can resume without repeating completed valid test cases.

Running the same manifest against the same camera/software fingerprint produces the same test-plan identity and comparable output structure.

## Recommended checkpoint commits

```text
feat: add manifest-driven qualification runner
feat: add resumable isolated hardware test execution
```

# 14. Phase 9 — rigorous crop characterization

## Goal

Determine the useful sensor crop space without confusing driver geometry acceptance with actual high-FPS performance.

The campaign is split into two stages.

## Stage A — geometry qualification

Determine:

- whether mutable crop exists;
- bounds;
- minimum accepted dimensions;
- width/height step or alignment;
- x/y alignment;
- whether requested rectangles are rounded;
- whether crop behavior changes by advertised sensor mode.

Prefer TRY-state probes where supported.

Store requested and negotiated rectangles for every probe.

## Stage B — performance qualification

Do not benchmark every possible x/y rectangle unless Stage A detects position dependence.

For each relevant crop size:

1. test a centered crop;
2. test representative edge/corner positions;
3. compare:
   - accepted geometry;
   - negotiated timing;
   - achieved FPS;
   - error behavior.

If position does not affect timing/capability, benchmark the size once.

If position changes behavior, expand position testing for that size/sensor.

This reduces redundant capture work while preserving rigor.

## FPS search

For each tested mode/crop:

1. establish a conservative working frame duration;
2. reduce frame duration until:
   - clamped;
   - rejected;
   - unstable;
3. refine the boundary;
4. run a longer final validation at the selected maximum stable configuration.

Record both requested and measured timing.

## Acceptance gate

The result dataset distinguishes:

- geometry accepted;
- geometry adjusted;
- capture starts;
- stable maximum FPS;
- processing/storage limitation;
- sensor/pipeline limitation.

No single `supported=true` field is allowed to collapse these different outcomes.

# 15. Phase 10 — official Raspberry Pi camera campaign

## Goal

Run the finalized qualification campaign once for each official Raspberry Pi sensor family available for the project.

Target families:

- OV5647 — Camera Module v1;
- IMX219 — Camera Module v2;
- IMX708 — Camera Module 3;
- IMX477 — HQ Camera;
- IMX296 — Global Shutter Camera;
- IMX500 — AI Camera.

Variants using the same sensor may be documented separately when a hardware difference is relevant, but should not automatically trigger a full duplicate low-level qualification.

## Campaign prerequisites

Before starting any official run:

- freeze the qualification manifest;
- tag or record the exact source commit;
- record OS image/version;
- record kernel;
- record libcamera version;
- record board model and RAM;
- record power/thermal conditions;
- use the same physical Pi configuration where possible;
- use a fixed visual test scene;
- verify no thermal throttling at baseline.

## Per-camera published artifacts

Publish:

```text
qualification/results/<platform>/<sensor>/<campaign-id>/
    environment.json
    camera.json
    plan.json
    results.json
    results.csv
    report.md
    samples/
        baseline.png
        representative-high-fps.png
        representative.dng
        slow-motion.mp4
```

Large raw captures do not have to be committed if repository size would become unreasonable.

The timing/configuration records and representative verification frames must be sufficient to audit the published conclusions.

## Acceptance gate

Every official sensor family has either:

- a completed qualification result;

or:

- a clearly documented blocked result explaining why the test could not be completed.

Do not silently omit an official model.

Implementation should use small checkpoint commits and push them to the current branch after meaningful milestones.

Good checkpoint boundaries include:

- build skeleton;
- inventory working;
- normal capture working;
- request lifecycle stable;

- high-FPS IMX296 regression;
- HSCAP writer;
- HSCAP reader;
- raw unpacking;
- PNG export;
- DNG export;

Avoid large commits that mix:

- API redesign;
- capture behavior;
- raw image processing;
- qualification policy.

No GitHub Actions workflow should be dispatched to validate these changes. Build and test directly in the local/Raspberry Pi environment.

# 20. Risk register

## Risk: libcamera reconfigures away the externally selected sensor crop

Mitigation:

- explicit operation ordering;
- re-read sensor state after libcamera configure;
- exact mode that fails rather than silently continuing;
- IMX296 regression test.

## Risk: camera drivers expose different crop semantics

Mitigation:

- runtime capability detection;
- generic V4L2 selection API first;
- sensor-specific quirk only after measured need;
- qualification captures requested and negotiated state.

## Risk: high-FPS callback path drops frames because of library overhead

Mitigation:

- completion callback does minimal work;
- fixed allocation before start;
- bounded queue;
- discard-payload performance mode;
- explicit overrun counters.

## Risk: stored raw frames cannot be reconstructed later

Mitigation:

- HSCAP stores negotiated format/planes/stride;
- fixed schema version;
- reader tests;
- visual verification required before qualification.

## Risk: demosaic output looks plausible while raw interpretation is wrong

Mitigation:

- synthetic bit-exact RAW10/RAW12 tests;
- all Bayer orders;
- stride fixtures;
- repeatable visual chart.

## Risk: qualification takes too long

Mitigation:

- separate geometry from performance testing;
- test position dependence before expanding x/y combinations;
- resumable campaign;
- test-plan identity and caching.

## Risk: software update invalidates published results

Mitigation:

- publish complete environment fingerprint;
- never present the result database as timeless hardware truth;
- allow a future campaign version to coexist with v1 results.

# 22. First coding task

The first implementation task after this roadmap should be:

```text
Phase 0 + the smallest part of Phase 1
```

Specifically:

1. add CMake;
2. add `libhscam`;
3. implement `Context`;
4. enumerate libcamera cameras;
5. add `hscam-inspect`;
6. run it on a Raspberry Pi before designing additional API surface.

That gives immediate feedback from the real libcamera API and avoids committing to abstractions that the actual Raspberry Pi camera stack does not support cleanly.
